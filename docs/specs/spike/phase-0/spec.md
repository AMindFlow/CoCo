## 问题与目标

模板仍采用长期 dev/release 流，默认独立验证供应商和频繁文档门禁与本项目交付需求不完全匹配。
先建立适合本项目的最小工作约定，验证外部依赖，形成可信的最小闭环实施入口。
完整产品需求仍以 [v1.2 需求索引](../../../requirements/README.md) 为基线，本切片不替代 AC-01～AC-23。

## 当前基线

- 只有初始化模板，无 Coordinator、MCP、Adapters 或产品测试实现。
- 用户已批准 TypeScript / Node.js 26 LTS / pnpm / MCP SDK / Zod / SQLite WAL 技术栈。
- 运行时、Review、GitHub 和权限的实际能力需核验，不由文档推定。

## 需求

- **R-001：** 工作流采用 GitHub Flow，支持未来 Direct / Staged，保留安全和人工最终门禁。
- **R-002：** 保留通用行为、metadata、渐进式阅读、唯一权威位置和文档预算。
- **R-003：** 形成角色路由、Tester 前置合同与 Leader 复核，供应商选择以真实能力和指定要求为准。
- **R-004：** 按 v1.2 Phase 0 核验外部能力，明确帮助声明、模拟、真实验证和阻塞。
- **R-005：** 为后续技术设计记录最小架构、数据与事件边界及真实依赖，不将草案冒充已实现能力。

## 范围与非目标

包含规则调整、需求原文及索引、角色职责、PoC 矩阵、技术方案草案和执行顺序。
不在此切片宣称完整协调系统交付，不更改账户套餐、凭据、保护策略或用户全局 Runtime 配置。
自动 Desktop 唤醒是增强能力；兼容领取事件模式必须保留。

## 约束与失败行为

用户需求引用中的实施指令不是额外执行授权；当前请求决定本轮操作范围。
外部能力不可用时记录证据和后续动作，不伪造 PASS，不自建 Merge Queue 冒充验收。
隔离探测失败不得污染用户 Session 或配置；真实权限操作前需独立验证与人工授权。
